## Callable API and limits

`ConvexWorkerClient(runtime_site_url, job_token, timeout_s=20.0, max_response_bytes=1048576)` retains all existing public methods/signatures. An HTTP(S) origin must have a hostname, optional valid port, and no credentials, non-root path, query, fragment, whitespace/control characters or malformed IPv6. Invalid construction returns fixed `ValueError` codes only. Timeout must be finite, positive and nonboolean. Response limit must be an integer (not boolean) in **1..1,048,576 bytes**, default **1,048,576 bytes**. Tokens must be nonempty printable ASCII without whitespace; they stay in memory/stdin/Authorization only, never process arguments, repr, logs or error messages. Client repr contains no origin or token.

- `get_job() -> WorkerJobResponse`: actual closed flat-input job/config/session/upload/turn/remark/completed-run projection, including required studentLabel and subjectRole.
- `heartbeat()`, `start_stage(...) -> stageRunId`, `finish_stage(...)`, `done(...)`.
- `persist_transcode`, `persist_turns`, `persist_plan`, `persist_moment`, `persist_target` (anchor or per-remark subject), `persist_track(cache_key=...)`, `persist_marks(provenance=...) -> {markId: annotationId}`, `persist_verdicts`, `persist_render`.

Lifecycle JSON request bodies are capped at **32,768 bytes**; persistence JSON envelopes at **1,048,576 bytes**, including metadata/JSON overhead, before any network work. Persistence outputs and provenance retain authoritative JSON Schema validation; lifecycle inputs retain parent preflight validation. Optional fields are omitted rather than null. Finite parsing, strict boolean success, closed shapes, pinned config matching, and exact marks-map validation are preserved. Pydantic/serialization validation details never escape client failures.

Response bodies are counted incrementally with at most 8,192-byte reads, stopping after the configured cap plus one detection byte. Missing Content-Length and exaggerated Content-Length do not bypass this cap. HTTP framing defines the response boundary; no decompression is performed. Truncated declared bodies fail closed. Header parsing additionally uses Python http.client's finite line/count limits. Requests are direct via http.client: environment proxies are ignored, TLS certificate verification uses the standard default, and **there are no automatic HTTP retries**. Every 3xx rejects before following Location, disposes the response/connection, and never forwards Authorization.

## Deadline and cleanup semantics

Each call owns a fresh stdlib-only Python child process with independent resolver/socket state, no shared executor or client lock, and bounded stdin/stdout data. Secrets are delivered through stdin; stderr is discarded and only fixed failure codes or capped successful response bytes cross stdout. HTTPException, invalid headers and all ordinary transport exceptions are sanitized inside the child.

A monotonic deadline starts after preflight validation and request-body serialization and includes envelope preparation, process startup, DNS, connect, TLS, request writes, response headers/body and child completion. The parent waits with the remaining budget; expiry returns fixed `TIMEOUT` after killing and reaping the owned process and closing its pipes. Normal completion closes response/connection and reaps the child too. Caller cancellation unwinds through the same finally cleanup. No resolver thread, socket, queued retry or abandoned child remains after a call. This intentionally trades one process startup per call for interruptible ownership of otherwise uninterruptible platform DNS. Heartbeats on the same client can proceed during a blocked call.

This is a network deadline, not a real-time scheduling guarantee: OS process creation, scheduling and kill/reap latency can add cleanup overhead; Python cannot guarantee a fixed wall-clock return bound if the OS itself stops scheduling or a process is stuck in an uninterruptible kernel state. Preflight validation and post-response JSON/model parsing are outside the network budget. Local regressions allow 0.50 seconds for a 0.20-second network budget (observed about 0.21–0.23 seconds including cleanup). Socket read timeouts alone are not claimed to enforce a total deadline. A timed-out POST may already have committed server-side; retry/idempotency decisions remain with the caller.

Fixed runtime codes include `CONTRACT_INVALID`, `REQUEST_TOO_LARGE`, `HTTP_STATUS`, `TRANSPORT_FAILED`, `TIMEOUT`, `RESPONSE_TOO_LARGE`, `INVALID_RESPONSE`, and `REDIRECT_REJECTED`; construction uses `INVALID_ORIGIN`, `INVALID_TIMEOUT`, `INVALID_RESPONSE_LIMIT`, `INVALID_TOKEN`.
